| REG-1773 (REG-S08b.2) | Data · the local database | **No write collision leaves the server holding the database's lock** — the bug S08's builder found, fixed at its root (`lib/db/local-file.ts`, used by `lib/db/index.ts`). Cause, reproduced: libsql opens every connection with **no busy timeout**, so a statement that meets another process's lock (a probe's `sqlite3`, `npm run db:repair` while a server runs) fails at once with SQLITE_BUSY; and @libsql/client runs each statement through `prepare().run()` while libsql-js **never resets a statement that failed** — the half-run statement stays active until the garbage collector happens to finalize it. SQLite then stops auto-committing every later write on that connection (they keep the write lock and stay invisible to other processes — a page's "seen" stamp after a collision never landed), or, after a COMMIT that failed and its ROLLBACK, keeps a SHARED lock on the transaction's own connection — on an idle server, until it restarts. The cure: **every connection waits up to 5 s for a lock** (`BUSY_WAIT_MS`, the client's `timeout`, also given to `scripts/migrate.ts` · `repair-demo-data.ts` · `snapshot-baseline.ts`); **a transaction ends through exec** (`EndsCleanly`: COMMIT / ROLLBACK through `executeMultiple`, which finalizes its statement even when it fails; a rollback after SQLite already ended the transaction is a no-op, so the first error is the one reported); **a statement on the main connection that still fails on a lock replaces that connection** (`reconnect`) before the error goes on; **`batch` runs on its own write transaction** ended the same way. A remote libSQL database is returned untouched. The harness (now the probe's section 7): before, 6 of 12 checks failed — an autocommit write and a page's transaction refused at once, the next writes never landing, a sqlite3 write locked out; after, a short lock is simply waited for (≈1.2 s), a lock held past 5 s fails that one write cleanly, and the file is free after every case. | bug fix |
