## 4. Room detection ("We found")

- How rooms are read: one vision call, model `google/gemini-3-flash-preview` (`route:29`), on the **hard** (line-art) scan, prompt `MANIFEST_PROMPT` (`route:31-41` qanvast) — strict JSON `{"rooms":[{"name","function","position","keyItems":[…]}]}`; one entry per enclosed space incl. balconies, stores, shelters, walk-in wardrobes, open-plan zones as ONE; `function` from a fixed vocabulary "bedroom, bathroom, kitchen, living-dining, living, dining, balcony, store, shelter, wardrobe, study, utility, entryway, corridor"; `position` one of 9 (top-left … bottom-right); `keyItems` only furniture actually drawn. Server sanitises: name required, lower-cases function/position, max 30 rooms (`route:94-104`). 45 s timeout; JSON-mode retry with a bigger token budget.
- Chips = `summarizeInventory(rooms)` (`inventory:63-74`), counting by function group (`inventory:15-22`), in this fixed order, a group shown only when its count > 0, then always a total:
  - bedrooms (function contains "bed", not "wardrobe") → **"1 bedroom"** / **"3 bedrooms"**
  - bathrooms ("bath", or exactly "toilet"/"wc") → **"1 bathroom"** / **"2 bathrooms"**
  - kitchen → **"Kitchen"** (bare when one) / **"2 kitchens"**
  - living ("living" or "dining") → **"Living/dining area"** (bare when one) / **"2 living/dining areas"**
  - balcony ("balcon" / "yard" / "patio") → **"1 balcony"** / **"2 balconies"**
  - storage ("store" / "shelter" / "utility" / "wardrobe") → **"1 storage room"** / **"2 storage rooms"**
  - always last: **"{n} rooms in total"** (n = every room incl. study, entryway, corridor, which have no chip of their own)
  - first letter capitalised (`inventory:57,70`). Example from the tests (`src/__tests__/floorplan-inventory.test.ts:55-63`): "3 bedrooms", "2 bathrooms", "Kitchen", "1 storage room", "8 rooms in total".
- Look: read-only pills, `px-3 py-1.5 rounded-full`, primary-variant fill, primary text, primary-variant-hover border; caption-s (plg) / text-xs (qanvast); no tap action on a chip. The edit pill sits at the end of the same row: outlined, `Pencil` 11px, **"Not quite right?"** ↔ **"Done editing"**.
- "Not quite right?" opens a **plain textarea (7 rows) holding the whole formatted inventory text** (the `manifest` string, §11) — NOT add/remove/rename/count controls. The user edits free text; "Done editing" just hides it (no save, no validation, no undo, no reset to detected).
- How edits reach the render: the textarea's current text **is** what is appended to the prompt (`pipeline:343`: `${template}\n\n${manifest.trim()}`); emptying it sends no inventory.
- **Caveats a port must decide on:**
  - The **chips do not change** after an edit (they are computed from the detected `rooms`, not from the text).
  - The **fidelity gate still scores against the detected rooms** (`planRooms: rooms`, plg `page:112`), not the edited text — so if the user corrects "3 bedrooms" to 2 and the model obeys, the gate counts a "missing bedroom", silently retries with a CORRECTIONS line pushing back toward 3, and may show the soft "may not match" note.
  - When nothing was detected, there are no chips and no edit pill, so the user cannot supply an inventory; generation runs ungrounded and un-gated.
- Spec intent (`spec.md:43-45`): "tap-to-correct (the room-inventory manifest in a human disguise). Correct → one regeneration with the corrected inventory." — built as the textarea above, and no automatic regeneration on correct (the user presses Generate).

## 6. Generating — words, time, cancel, charges, limits

- Words: **"Creating your 3D floor plan… this takes about half a minute."**; plg's step chips (§2.4). Idle promises "~30 seconds"; header "in under a minute".
- Time: spec ~10–25 s single shot, ~40 s with the retry. Route timeouts: image 110 s (`route:310`), manifests 45 s, `maxDuration = 120` (`route:2`).
- **Cancel: none.** Reset is only reachable from Confirm/Result/Error; navigating away is the only escape (a late result is then dropped by the run token only if a reset/new upload happened in the same page).
- What runs per press of Generate / Regenerate / Try again / a style switch (`pipeline:335-384`, `generateWithGate`):
  1. generate (`google/gemini-3.1-flash-image`, `pipeline:342`) with the soft scan + prompt; the route itself retries once on an empty image (`route:315-337`); output aspect ratio bucketed from the scan's size (16:9 · 3:2 · 4:3 · 1:1 · 3:4 · 2:3 · 9:16).
  2. if rooms were detected: score — re-read the render with `RENDER_INVENTORY_PROMPT` (`route:44-54`) and `diffInventories(plan, render)`: checks "rooms" (total) + each group present on either side, bedrooms and bathrooms always (`inventory:31-43`).
  3. if not a full match: ONE silent corrective retry with `CORRECTIONS — a previous attempt failed these checks, fix them:` + one line per failed check; keep the second only if it scores strictly higher, else the first (`pipeline:364-379`).
  4. scoring errors fail OPEN (render shown, `fidelity: null`, no note).
  - So 1–4 billable AI calls per press (+1 room read per upload).
- **Charges: nothing.** No credits are spent, no refund logic, no price shown (§1.4). plg records each OpenRouter attempt in its AI-usage sink (`src/lib/ai.ts` → `src/lib/ai-usage.ts`, per-tool tags `floorplan-3d-sandbox/manifest-plan|render`) — cost accounting only.
- Limits:
  - file types: JPG, PNG, WebP only (`accept`); no PDF, no HEIC handling in code (an undecodable file fails at the scan → scan error message).
  - size: browser downscales to ≤2048 px JPEG first; server cap 14,000,000 base64 chars, said as **"Image too large (max 10MB)"** (`route:218`); prompt ≤6000 chars (`route:26`) — the full prompt (template + manifest, and on retry + corrections) is authored in the browser.
  - rate: 30 requests / minute / IP on one key shared by every call of the tool (`route:160`; window default 60 s, `src/lib/rate-limit.ts:1-2`). One upload + render = 3–5 calls.
  - session required (cookie `qanvast_session`).
  - multi-floor, measurements, furniture choice: out of scope (`spec.md:28-29`).
- Spec's "Never a dead end" soft note: shown on Result (§7).

## 11. Render prompt and inventory format (2.0 already copies these — notes only)

- Composition (`pipeline:343`): `prompt = template + "\n\n" + manifestText.trim()` when the inventory text is non-blank, else the template alone. Retry (`pipeline:367`): `prompt + "\n\nCORRECTIONS — a previous attempt failed these checks, fix them:\n" + lines`, each line `"{label}: the plan has {p}, the render has {r} ({invented extra|missing} {label})"` (`inventory:77-81`).
- Templates: `LOCKED_ISO_PROMPT` (`pipeline:25-50`, = spec Appendix A: CORE FIDELITY REQUIREMENTS · VIEWPORT & CAMERA "Three-quarter view from above (45-degree elevation)", "ORIENTATION LOCK … PARALLEL to the image edges", "Cut walls at a consistent height (no ceiling)" · INTERIOR & STYLE "Furnish every space according to the per-plan room inventory provided", "modern, tasteful interior style", "clean, neutral solid color" background · STRICT NEGATIVE CONSTRAINTS "NO TEXT", "NO FABRICATION" · RENDER QUALITY & CONTEXT "PHOTOGRAPH-QUALITY", "NO SURROUNDINGS"); `PHOTO_TOPDOWN_PROMPT` (`pipeline:52-65`: "bird's-eye … straight down … (90 degrees overhead, no perspective tilt)", no ceiling, axis-aligned, exact footprint, "FIDELITY CHECK … same number of bedrooms, … bathrooms, and the same kitchen position", furnish by function, NO TEXT, soft daylight, + the same RENDER QUALITY & CONTEXT block).
- Inventory text = `formatManifest(rooms)` on the server (`route:108-123`):
  ```
  ROOM INVENTORY — detected from the plan. Your render must contain EXACTLY these rooms and nothing else:
  1. {name} ({position}): {keyItem, keyItem}
  …
  Totals: {n} rooms in all · {b} bedroom(s) · {w} bathroom(s)/WC(s).
  HARD RULE: do NOT add any extra bedroom, bed, bathroom, wall, or room that is not in this inventory. Do NOT merge, split, or omit any listed room. Each room's furniture must match its listed key items.
  This inventory is LAYOUT INFORMATION ONLY — do NOT write any of these names, or any other text, label, caption, or annotation, anywhere in the render. The output must be a clean photorealistic image containing ZERO text.
  ```
  (position in brackets only when present; ": items" only when any).
- **Room edits and the prompt:** the user edits exactly this text in the textarea; the edited text replaces it verbatim in the prompt. The Totals line is NOT recomputed from an edit (the user would have to fix it by hand), the chips are not recomputed, and the gate still compares against the detected rooms (§4).
- No style-reference image, no studio exemplar, no free text from the user other than the inventory textarea; the template is sent from the browser (spec §4 wanted it server-side — not done).
- DRY_RUN / no `OPENROUTER_API_KEY` (`route:225-232, 299-307`): room read returns three mock rooms (Living/Dining bottom-left: sofa, round dining table · Bedroom 1 top-right: double bed · Bathroom centre: toilet, shower → chips "1 bedroom", "1 bathroom", "Living/dining area", "3 rooms in total"), and the "render" is the input scan echoed back.

## 12. Everything else a 2.0 port could miss

1. **Generic upload of the studio's own plan IS the product** — there are no sample plans in 1.0; every run reads the user's photo end to end (paper detect → deskew → clean → rooms → render).
2. **Two scan variants:** the user sees the cleaned line-art; the model gets the natural "soft" scan (anti-sketch). Showing one and sending the other is deliberate.
3. **Room read can fail without failing the tool** — Confirm then shows "We couldn't auto-detect the rooms — you can still generate, or upload a clearer photo." and Generate runs ungrounded.
4. **The silent fidelity gate + one corrective retry + best-of-two**, and the soft "may not match" note when it still misses; scoring errors never block a render.
5. **"Try again" on the Error card** re-runs only the render (keeps the scan), shown only when a scan exists; scan errors offer only "Upload a different plan".
6. **The style switch on Result regenerates at once**, even on the already-selected style (a second Regenerate path).
7. **Edited inventory survives Regenerate and style switches** within the session (state), but there is no editor on Result and Start over drops it.
8. **"Use a different plan" (Confirm) / "Start a new plan" or "New plan" (Result) / "Upload a different plan" (Error)** — three wordings of reset, no confirmation.
9. **Download** names the file `3d-floor-plan.png`.
10. **The plan is shown faded while rendering** (keeps the user's plan in view).
11. **plg's idle page teaches**: What you'll get (two fixed examples) + How it works (3 steps), and the progress step chips.
12. **No credits are charged** (the route is exempt) although plg's pricing page lists the tool as "tokens" on every plan — a 2.0 port must decide whether it is metered and show the price before the press if so.
13. **Rate limit 30/min/IP** shared across every call the tool makes; a fast user can hit "Too many requests" (shown as the generic render error).
14. **Never call it a "3D model"** (spec naming rule) — the output is an image; words used: "3D view", "3D floor plan", "3D render".
15. **Beta everywhere** it appears (nav tiles, header, pricing row with "(Beta)" pinned by a test).
16. **Not built in 1.0 although in its spec** (so not a parity gap, but likely asked): drag-drop / paste / camera intake; "Adjust corners" rescue; ±90° flip; project/lead binding with auto-filing into Renders; "Share to portal"; server-side orchestration route; per-studio style reference; tap-to-correct chips (built as a raw textarea); labeled-overlay conditioning, geometry scaffold, LoRA (spec §7 future).
17. **Staff-only sandbox** `/tools/floorplan-3d-sandbox` (both; any owner/admin/id can type the URL, it is in no nav) carries the calibration knobs: original vs straightened scan, angle slider + 90° flips + Back to auto, paper extraction toggle, corner editor, AI redraw comparison, geometry scaffold (vectorize → extrude, "Step 1.5"), model picker (Gemini 3.1 Flash only), editable prompt templates + "improve prompt" optimiser, style reference upload, editable inventory with placeholder "No inventory detected — write one, or Generate runs without grounding.", per-run scorecards ("Fidelity check failed — result unscored."). None ship in the tool (spec `spec.md:35-36`: "The sandbox's knobs are calibration scaffolding — **none of them ship**").
18. No keyboard shortcuts, no analytics events, no Maison AI hooks, no loading/error route files, no ghost/skeleton — the page is a single client component.
