## Bottom line

- **A project is one wide row plus JSONB.** `projects` has ~60 columns; the milestones (the Gantt, the payment schedule, publish snapshots, comments, dependencies) live in **`projects.timeline` JSONB**, not in a table. `project_milestones` survives only as a sparse side table that holds the homeowner's approve / revision answer, keyed by the timeline's own ids (J-22…J-25).
- **Three "status" fields, one of which matters.** `stage` (text: `Draft` → `Active` → `Closed`) is the lifecycle. `status` (enum, born `planning`) is legacy and is never moved by closure, yet the rail badge, the dashboard widget and the listing's "Planning" pill still read it. `closure_status` (`pending_review` / `approved` / `rejected`) and `archived_at` sit beside them (J-07…J-12).
- **The effective schema is the union of two migration sets that disagree.** `scripts/…/089` drops the `stage` CHECK that `supabase/…/20260503000002` adds; `project_files` and `project_selections` are created twice with different shapes; `notifications` three times; `closed_at` is written by the closure route but **no migration creates it** (J-286…J-296).
- **Only three project routes check a role** (archive, unarchive, delete → Owner or Admin). Everything else — create, edit, timeline, assignees and commission splits, closure approve / reject, review of progress updates, milestone invoices, project types — accepts any signed-in studio member (J-151…J-160).
- **"Designers see only their projects" is a browser filter.** `GET /api/projects/records` returns every project of the studio; `app-context.tsx` filters by assignee for ID-only users. The detail and money routes take any project id (J-161, J-162).
- **Money is not hidden on the server.** `project-aggregates/financial-summary` and `activity-feed` return invoices, payments, PO totals, expenses and commission rules to any member (J-163).
- **The handover lock is a client flag.** `projects.handover_locked_at` is never written anywhere; the lock is `lockProjectOnHandover && stage === "Closed"` in the page, with no server check (J-17, J-164).
- **Notifications:** two project events of its own (`project.progress_update_submitted`, `project.timeline_published`) plus milestone, selection, questionnaire, floor-plan, invoice, VO and task events; studio side through `dispatchNotification` (bell · email · opt-in WhatsApp), homeowner side through direct rows in `homeowner_notifications`. No milestone-due or project-due reminder exists; the only time-based ones are the task T−30 reminder and the daily invoice-overdue cron (J-169…J-200).
- **Tasks carry the approvals.** Closure, progress review, commission, invoice review and milestone approval are `tasks` rows of special `type`s, not notifications (J-27, J-190).
- **Dead or half-built:** `project_snag_items` (no code), `homeowner_notification_preferences` (no code), `studio_timeline_templates` (no screen), `projects.project_type_id`, `projects.progress_updates` JSONB, `payment_schedule_rebalance_log`, `/api/projects/templates/*` (superseded twin), the offline queue (no producer), `usePortfolioKPIs` (J-306…J-316).
- **Likely live defects [inferred]:** migration 264 revokes `milestone_templates` from the role the project-types route uses; the mAIson bot's `create_project` inserts without `project_seq_id` (NOT NULL); Clone drops `company_id` and the entity lock then freezes it empty; `projects.updated_at` never moves (J-297…J-305).
- **For 2.0:** the core is `projects`, `project_assignees`, a milestones table in place of the JSONB, tasks (2.0's `lead_tasks` already allows a null lead), `progress_updates`, `project_files`, `project_selections`, `studio_milestone_templates`. Finance and the homeowner portal are separate modules that hang off `project_id` (J-269…J-285).

## 1. Data model

### 1.0 How the schema is assembled

- **J-01** Two migration sets exist and both are applied by hand: `supabase/migrations/` (timestamped, "local") and `scripts/migrations/` (numbered, "production"); the handbook tells developers to copy each new file from the first into the second (`docs/DEVELOPER_HANDBOOK.md:291-294`, `docs/DATABASE_SCHEMA.md:1052`). There is no single ordered history, so the order in which two files touching the same object ran is not recorded in the repo.
- **J-02** The first 22 files are twins. Diffed: `006_projects.sql` differs only in `quote_line_items.unit_price` (`numeric(12,2)` vs `integer`, line 120); `001_enums.sql` differs in the `property_type` enum (line 16); 017, 030, 032, 033, 011 and 012 are identical to their `supabase` twins.
- **J-03** Later work landed in only one set each: e.g. project sequence ids, stage values, closure, satisfaction, commission toggle, rooms, selections, templates and the homeowner portal are only in `supabase/migrations/`; archive, handover lock, company / entity lock, country code, multi-assignment, files alignment, the RLS lock wave and finance are only in `scripts/migrations/`.
- **J-04** No SQL views exist anywhere in either set (searched `create … view`). Aggregates are computed in route handlers and hooks.
- **J-05** Tenant isolation is by RLS keyed on a short-lived JWT the server mints per request: `scopedSupabase(studioId)` signs `{ role: "authenticated", studio_id }` (HS256, 60 s) and Postgres policies compare `studio_id` with `auth.jwt()->>'studio_id'` (`src/lib/supabase-scoped.ts:35-92`, `scripts/migrations/226_lock_tenant_tables.sql:35-72`). Routes that use `createServerSupabase()` (service role) bypass RLS and rely on their own `.eq("studio_id", …)`.

### 1.1 Enums and status vocabularies

- **J-06** Postgres enums that touch Projects (`scripts/migrations/001_enums.sql`): `project_status` = `planning · hacking · in_progress · completed · on_hold · cancelled` (line 32); `milestone_status` = `upcoming · in_progress · completed · delayed` (36); `payout_model` = `none · percentage · fixed` (40); `split_logic` = `equal · custom` (44); `time_unit` = `days · weeks · months` (88); `project_category` = `residential_hdb · residential_condo · residential_landed · commercial` (92).
- **J-07** `projects.stage` is the lifecycle and is plain text. Born `Design / Execution / Closed` with default `Design` (`scripts/migrations/017_projects_and_leads_extended.sql:22`), changed to `Draft / Active / Closed` with default `Draft` (`supabase/migrations/20260503000002_project_stage_values.sql:5-21`), legacy rows normalised to `Active` or `Draft` (`scripts/migrations/186_normalize_project_stage.sql:27-33`). The UI type is `'Draft' | 'Active' | 'Closed'` and anything unknown reads as `Active` (`src/types/app.ts:285`, `src/lib/transformers.ts:457-467`).
- **J-08** `projects.status` (enum, default `planning`) is legacy: the create route always writes `"planning"` and `current_phase: "Planning"` (`src/app/api/projects/records/route.ts:272-273`), the closure route never touches it (`src/app/api/projects/records/[id]/closure/route.ts:72-80`), and the listing's "Planning" pill is `formatStatus(db.status)` (`src/lib/transformers.ts:103-108`, `:500`). The listing groups by `stage` first and only falls back to `status` (`src/app/(main)/projects/page.tsx:86-100`).
- **J-09** Draft → Active is automatic. At insert the route promotes to `Active` when an assignee, a quote status other than `none`, a contract file name, a seeded timeline and `commissionLocked === true` are all present (`src/app/api/projects/records/route.ts:255-263`); the detail page repeats the check later and flips the stage when every setup gate is done (`src/app/(main)/projects/[projectId]/page.tsx:1558-1575`).
- **J-10** Closure: `closure_status` is `pending_review` (submitted), `approved` (also sets `stage = 'Closed'`, `closed_at`, `closure_approved_by/at`) or `rejected` (keeps the stage, stores the comment and — oddly — stamps `closure_approved_by/at` with the rejecter) (`supabase/migrations/20260503000016_closure_summary.sql:5-6`, `src/app/api/projects/records/[id]/closure/route.ts:52-80`, `:167-175`).
- **J-11** Archived is `archived_at IS NOT NULL` (`scripts/migrations/099_projects_archived_at.sql:13`); the list route returns either the live set or the archived set (`?includeArchived=1` means archived only) (`src/app/api/projects/records/route.ts:66-83`).
- **J-12** Other small vocabularies: `timeline_status` `draft · submitted · approved` (workflow removed May 2026, column kept) (`017:25`, `supabase/migrations/20260509000001_remove_timeline_approval.sql:30-37`); `quote_status` on the project `none · draft · submitted · approved · rejected · sent_for_signature · client_signed` (`017:30`, `scripts/migrations/068_project_quote_status_constraint.sql:7-17`); `commission_payout_mode` `closure · phase_wise` (`supabase/migrations/20260503000012_commission_toggle.sql:4-5`).
- **J-13** Milestone status in the timeline JSONB is a different vocabulary from the enum: `not-started · in-progress · completed · pending-approval · blocked` (`src/types/app.ts:1388`), against `milestone_status` `upcoming · in_progress · completed · delayed` on the legacy table (J-06).

### 1.3 Milestones, timeline, plan

- **J-22** A milestone is an object in `projects.timeline`: `id, name, order, startDate, endDate, status, description, comments[], color, tasks[] (deprecated), paymentPercent, type ('fixed'|'percent'), amountCents, commissionTrigger, milestoneKind ('work'|'payment'), sourceCategory, baselineStartDate/EndDate, dependsOn[], dependencies[{fromMilestoneId, lagDays}], clientVisible, blockedBy{reason, details, blockedAt, expectedResumeDate}, finalizedAt, publishedAt, publishedSnapshot{name,startDate,endDate,status}, publishHistory[{at, changes[]}]` (`src/types/app.ts:1376-1488`).
- **J-23** The timeline is seeded at creation from the quote's payment schedule: one milestone per stage with `status: "not-started"`, empty dates, `paymentPercent` and `commissionTrigger: true`; a generic stage name ("1st payment", "Stage 2", "M3") is replaced by a name derived from its trigger text (`src/app/api/projects/records/route.ts:35-58`, `:241-253`).
- **J-24** `project_milestones` (legacy table): `id, project_id → projects CASCADE, template_id → milestone_templates, name, order_index, status milestone_status, planned_/actual_ start/end dates, payment_percent, payment_due_criteria text[], notes_to_homeowner, payout_model, payout_percent, payout_fixed_amount, payout_triggers text[], eligible_roles text[], split_logic, created_at, updated_at` (`scripts/migrations/006_projects.sql:60-82`) plus `homeowner_approval_status` (`approved | revision_requested | NULL`), `homeowner_approval_comment`, `homeowner_approval_at` (`supabase/migrations/20260419000005_homeowner_milestone_approvals.sql:4-9`).
- **J-25** Today that table is a sparse store for the homeowner's answer: the portal route finds the milestone in the timeline JSONB, then updates or inserts a row with the same id carrying only name, order and the approval fields (`src/app/api/homeowner/projects/[id]/milestones/[milestoneId]/approve/route.ts:57-149`). Foreign keys from other tables to it were dropped for that reason (`supabase/migrations/20260515000001_invoice_milestone_id_soft_ref.sql:13-14`, `scripts/migrations/149_progress_updates_drop_milestone_fk.sql:18-19`, `211_drop_milestone_fks.sql:35-36`) — except `tasks.linked_milestone_id`, which still has one (J-298).
- **J-26** The AI plan is not stored as rows: `POST /api/projects/plan` returns milestones plus tips, and the client saves them into `timeline` and `ai_plan_metadata`; `POST /api/projects/plan/tasks` returns up to eight task titles for one milestone (`src/app/api/projects/plan/route.ts:226-300`, `src/app/api/projects/plan/tasks/route.ts:294-385`).

## 3. Roles

- **J-151** Roles are tags on `studio_members.tags`: `owner · admin · id · accounting · manager` (`src/lib/access-control.ts:15`). A studio may also have `studio_roles` rows whose `permissions` JSON (pages · dataScope · actions) takes precedence on the client; a missing action falls back to the tag rules (`access-control.ts:249-313`).
- **J-152** Page access to `/projects`: Owner, Admin, Designer (`id`) — not Accounting (`access-control.ts:68`; seeded role pages in `scripts/migrations/109_seed_default_system_roles.sql:15-18`, `:50-56`, `:82-86`, `:113-116`). This is a client route guard in the main layout (`src/app/(main)/layout.tsx:131-143`); no API route repeats it.
- **J-153** Seeded action permissions for projects — Owner `create · edit · delete`; Admin `create · edit` (no delete); Designer `edit` only; Accounting none; `project_override.override_lock` and `payment_schedule.override` for Owner and Admin (`109_seed_default_system_roles.sql:27-33`, `:60-66`, `:91-97`, `:122-128`; tag fallback `access-control.ts:329-347`).
- **J-154** Where the client applies them: `projects.edit` gates only the Team card (`src/app/(main)/projects/[projectId]/page.tsx:815`, `:2186`); `override_lock` lifts the handover lock (`:810-813`); `payment_schedule.override` unlocks a frozen payment schedule (`:825`, `:2775`); Delete is shown to Owner or Admin by tag (`:655-657`). `projects.create` and `projects.delete` are never consulted: the New Project button renders for everyone (`src/app/(main)/projects/page.tsx:309-311`).
- **J-155** Owner-only on the client: the Table / Workload toggle and the portfolio KPI strip with "Total Pipeline" (`projects/page.tsx:291-315`, `:404`); approve / reject closure (`[projectId]/page.tsx:1975-1984`); the Draft setup card's owner actions (`:1994`); set a custom commission rate at creation — a non-owner's rate becomes a change request (`src/components/projects/project-create-drawer.tsx:418`, `:500`, `:1125-1128`); the extension-request path differs for non-owners (`src/components/projects/gantt-chart.tsx:1878`).
- **J-156** Verifying a payment in the project's Finance tab: Owner, Admin or Accounting (`[projectId]/page.tsx:3871`); approving a milestone-completion step: Accounting (`src/components/projects/milestone-completion-status.tsx:165`).
- **J-157** Server-side role checks in the Projects API: archive, unarchive and delete require Owner or Admin by tag (J-82…J-84). The archive route's header explains that it deliberately does not use `projects.delete`, which would silently narrow it to Owner (`src/app/api/projects/[id]/archive/route.ts:14-18`).
- **J-158** Progress-update review is the one workflow rule the server resolves: Owners are always approvers; otherwise the member must be in `workflow.approvers.progressUpdate`; with review off, or an approver posting, the update is born approved (`src/lib/access-control.ts:563-593`, `src/app/api/projects/[id]/progress-updates/route.ts:146-159`). The later approve / reject call is unguarded (J-98).
- **J-159** The mAIson bot repeats a coarse rule: `create_project`, `update_project`, `create_task` need one of `owner · admin · id` (`src/lib/agents/executors.ts:2382`, `:2496`, `:2531`).
- **J-160** The requirements sheet records the same picture per feature: Overview edits "NOT role-gated", Gantt "Same as Admin" for Designers, milestone invoicing reachable by Designers from the project page though they cannot open Finance Operations, and `canMarkComplete` exempting only the literal Owner tag (`docs/openmaison-v1-feature-requirements.csv` rows 45–48).
- **J-161** Data scope ("Designers see assigned only") is applied in the browser: `filteredProjects` keeps projects where the member is in `assignees` or equals `assignedTo` when the user is ID-only (`src/context/app-context.tsx:135-143`); the list route itself returns all (J-70). Tasks are filtered the same way by `assigneeUserId` (`app-context.tsx:1169-1174`).
- **J-162** **[inferred]** Nothing on the detail page or in `GET /api/projects/records/[id]` checks assignment, so an ID-only member who has a project's id can open it and every sub-route (searched the page for any access guard; none found).
- **J-163** Money visibility by role is a client matter only. Finance pages are closed to Designers by route (`access-control.ts:110-122`), but the project's Finance tab and the aggregate routes that feed it have no role filter (J-124, J-125), and Designers reach milestone invoicing from the Gantt (J-109, J-160).
- **J-164** The handover lock is enforced in five client choke-points of the Gantt and in the progress widget via an `isLocked` prop (`docs/rules/projects.md:74`, `:85`); the API accepts the same writes on a closed project.
- **J-165** External parties: the homeowner authenticates separately (`homeowner_session`, phone + OTP) and reaches a project only through an active `homeowner_project_links` row (`src/app/api/homeowner/projects/[id]/milestones/[milestoneId]/approve/route.ts:14-45`); any studio member can open a 30-minute read-only preview-as-homeowner session (`docs/openmaison-v1-feature-requirements.csv` row 63); vendors reach POs by token (`/po`), clients reach the older pay page by token (`/pay`).
- **J-166** Managers (`manager` tag) are a Dyel-only lead hierarchy; no Projects code reads the tag (`access-control.ts:39-45`).

## 4. Notifications and crons

### 4.1 The machinery

- **J-169** One dispatcher: `dispatchNotification(eventType, payload)` runs after the response (`after()`), skips demo studios, honours a studio pause, reads per-category channel preferences, resolves recipients, drops duplicates inside 120 s, then writes the in-app row and sends email and WhatsApp per recipient (`src/lib/notifications/dispatch.ts:72-430`, `dedupe.ts:40`).
- **J-170** Recipients for a `project` entity = members whose tag is in the category's `recipient_roles` and who may open `/projects`, plus the project's assignees (junction first, scalar fallback), plus any `fixedRecipientIds`; the actor is not excluded (`src/lib/notifications/resolve-recipients.ts:27-32`, `:143-172`, `:384-426`).
- **J-171** Defaults when a studio has no preference row: in-app and email on for role `owner`; WhatsApp off (`src/lib/notifications/preferences.ts:80-104`). Category for project events is `projects`; tasks and escalations share `tasks_escalations` (`events.ts:115-125`).
- **J-172** The bell text is generic: title = `"<event label>: <entityLabel>"`; body = `entityLabel` unless the event has its own sentence (`dispatch.ts:434-507`).
- **J-173** WhatsApp goes through 360dialog (`D360_API_KEY`); proactive sends need an approved template, and only twelve events have one — of the project family: `task_assigned_internal`, `task_due_reminder_internal`, `milestone_homeowner_revision_requested_internal`, `vo_client_approved_internal`, `vo_client_rejected_internal`, `invoice_overdue_internal`, `invoice_payment_received_internal` (`src/lib/notifications/templates/whatsapp.ts:87-136`, `src/lib/360dialog.ts:49-114`).
- **J-174** Homeowner bell rows bypass the dispatcher: helpers in `homeowner-binding.ts` insert one `homeowner_notifications` row per active link of the project (`src/lib/homeowner-binding.ts:199-246`).

- **J-272** Names not worth keeping: `status` (`project_status` enum), `current_phase`, `progress`, `is_delayed`, `next_milestone`, `thumbnail_url`, `budget_used` are legacy display fields the detail page no longer drives; `assigned_to` / `assigned_designer` are deprecated mirrors; `timeline_status`, `progress_updates` (JSONB), `project_type_id`, `payment_schedule_rebalance_log`, `handover_locked_at` have no live writer. If the 1.0 developers need them for the data port, keep them as nullable pass-through columns only.
- **J-273** Milestones: 1.0's JSONB array is rewritten whole on every edit (J-74) and other tables point at its ids without a foreign key. In SQLite a `project_milestones` table with the JSONB's field names (`name`, `order`, `start_date`, `end_date`, `status`, `payment_percent`, `type`, `amount_cents`, `commission_trigger`, `milestone_kind`, `client_visible`, `blocked_*`, `finalized_at`, `published_at`, `published_snapshot`, `baseline_*`) gives real references for tasks, updates and invoices, and the 1.0 table of that name already carries the homeowner approval columns. The data port is then a flatten of each `timeline` array, keeping the ids. This is a divergence from 1.0's storage that the developers should agree to.
- **J-274** Enums → text columns with the value list in one TypeScript module (1.0 itself moved from enums and CHECKs to free text, `scripts/migrations/089_remove_enum_constraints.sql:1-32`). Stage: `Draft · Active · Closed`.
- **J-275** `text[]` (milestone template criteria, payout triggers, eligible roles, `receipt_urls`, `photo_urls`, `document_urls`) and `jsonb` (`timeline`, `quote_data`, `ai_plan_metadata`, `closure_summary`, `closure_deferred_items`, `options`, `attachments`, `metadata`, `payload`, `template_data`) → JSON text in SQLite, parsed in the data layer; anything the product filters or joins on should become a column or a table.
- **J-276** `uuid` → text ids; `timestamptz` → integer timestamps (2.0's convention, `lib/db/schema.ts:1205`); `date` → ISO text; `numeric(5,2)` percentages → integer basis points or a real; money in **cents** — note `projects.budget_total` is whole currency units in 1.0 (J-14).
- **J-277** RLS has no SQLite equivalent: tenant and role checks move into the server actions. 1.0's lesson is that the actions must also check the role and the assignment, which its routes do not (J-151…J-163).
- **J-278** Triggers to re-express in code: country fill and lock (J-15); entity lock (J-16); invoice money recompute and status guard (J-58, Finance); the lead → homeowner auto-bind (J-50, portal). None is needed for a first Projects build except "issuing entity is fixed once the project exists".
- **J-279** RPCs: `next_project_seq_id` → a per-studio counter read and incremented inside the insert's transaction (2.0 has the pattern in `nextSequence`, named in the 2.0 `CLAUDE.md` Settings notes). The one-project-per-lead rule should be a unique index on `projects(lead_id)` where the lead is set, which 1.0 lacks (J-18).
- **J-280** Activity: 1.0 derives it (J-46) and loses field edits and archive events (J-47). 2.0's house rule is the same derivation plus `lead_events` for what leaves no record; a project needs the equivalent event rows for edits, assignee removals, archive / restore, deletes.
- **J-281** Notifications: 2.0 has its own `notifications` table and event model; map 1.0's project events (J-175…J-190) onto it and keep the approval-as-task pattern, which 2.0's Tasks already support.
- **J-282** Files: 1.0 merges lead files into the project's list at read time (J-31). 2.0's `lead_files` already has folders and an image store; the simplest port keeps one file table per owner and repeats the merge.
- **J-283** Storage keys embed the studio and project ids (`<studio>/<project>/<folder>/<uuid>-<name>`); a port of the files needs the same path or a mapping table.
- **J-284** Postgres `ON DELETE` choices to carry over deliberately: children that are the project's own content cascade; tasks, conversations, escalations, render jobs and co-pilot sessions survive with a null project (J-62); finance rows block deletion (J-60).
- **J-285** Regions: `country_code` on the project decides currency, tax and compliance data (J-238). 2.0 is Singapore-only today; keep the column so the port is lossless.
